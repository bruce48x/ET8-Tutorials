# 客户端如何热更

这篇带你走一遍客户端热更的完整流程：从代码修改、`ET/Compile` 生成 dll.bytes，到运行中的 Unity 加载新代码。

先记住结论：客户端热更的目标是替换 `Unity.Hotfix.dll` 和 `Unity.HotfixView.dll` 这两个程序集。`ET/Compile`（F6）编译代码并生成 dll.bytes，运行时由 `CodeLoader` 加载，`ET/Reload`（F7）在运行中触发重载。

和服务端热更的对比记这个：

```text
服务端：写代码 -> dotnet build -> Bin/Hotfix.dll -> 控制台 ReloadDll -> CodeLoader.Reload()
客户端：写代码 -> ET/Compile(F6) -> Assets/Bundles/Code/*.dll.bytes -> F7 或 CodeLoader.Reload()
```

## 1. 哪些程序集参与客户端热更

客户端关注四个热更程序集：

```text
Unity.Model        — 不依赖 Unity 表现层的稳定类型（Entity、Component、协议、配置）
Unity.ModelView    — 客户端表现层的稳定类型（UI Component 字段定义）
Unity.Hotfix       — 不依赖 Unity 表现层的可热更逻辑（Handler、System、玩法规则）
Unity.HotfixView   — 客户端表现层的可热更逻辑（UI 创建、按钮响应、界面切换）
```

这四个名称定义在：

```text
Unity/Assets/Scripts/Editor/Assembly/AssemblyTool.cs
```

```csharp
public static readonly string[] DllNames = { "Unity.Hotfix", "Unity.HotfixView", "Unity.Model", "Unity.ModelView" };
```

这四个程序集**全部**会被 `ET/Compile` 编译并复制成 `.dll.bytes`，放到：

```text
Unity/Assets/Bundles/Code/Unity.Model.dll.bytes
Unity/Assets/Bundles/Code/Unity.Model.pdb.bytes
Unity/Assets/Bundles/Code/Unity.ModelView.dll.bytes
Unity/Assets/Bundles/Code/Unity.ModelView.pdb.bytes
Unity/Assets/Bundles/Code/Unity.Hotfix.dll.bytes
Unity/Assets/Bundles/Code/Unity.Hotfix.pdb.bytes
Unity/Assets/Bundles/Code/Unity.HotfixView.dll.bytes
Unity/Assets/Bundles/Code/Unity.HotfixView.pdb.bytes
```

但实际热更的主要是 `Hotfix` 和 `HotfixView`。`Model` 和 `ModelView` 更偏稳定定义，通常编译一次后较少变化。

## 2. 三种代码加载模式

客户端 `CodeLoader` 在 `Unity/Assets/Scripts/Loader/CodeLoader.cs`。它根据不同运行环境有三种加载路径。这是理解客户端热更最核心的一点。

**模式一：非 Editor（真机 / 打包后运行）**

```csharp
// CodeLoader.DownloadAsync()
this.dlls = await ResourcesComponent.Instance.LoadAllAssetsAsync<TextAsset>(
    $"Assets/Bundles/Code/Unity.Model.dll.bytes"
);
this.aotDlls = await ResourcesComponent.Instance.LoadAllAssetsAsync<TextAsset>(
    $"Assets/Bundles/AotDlls/mscorlib.dll.bytes"
);

// CodeLoader.Start()
byte[] modelAssBytes = this.dlls["Unity.Model.dll"].bytes;
this.modelAssembly = Assembly.Load(modelAssBytes, modelPdbBytes);
// 对 hotfix 同理
hotfixAssBytes = this.dlls["Unity.Hotfix.dll"].bytes;
hotfixAssembly = Assembly.Load(hotfixAssBytes, hotfixPdbBytes);
```

从 `Assets/Bundles/Code/` 目录加载 `.dll.bytes` 文件。如果是 IL2CPP 平台，在此之前还会加载 AOT 元数据。

**模式二：Editor + EnableDll = true**

```csharp
byte[] modelAssBytes = File.ReadAllBytes(Path.Combine(Define.CodeDir, "Unity.Model.dll.bytes"));
// Define.CodeDir = "Assets/Bundles/Code"
this.modelAssembly = Assembly.Load(modelAssBytes, modelPdbBytes);
```

直接从文件系统读 `Assets/Bundles/Code/` 下的 dll.bytes。这在 Editor 下模拟真机行为，方便测试 dll 加载模式是否正常。

**模式三：Editor + EnableDll = false（默认）**

```csharp
Assembly[] assemblies = AppDomain.CurrentDomain.GetAssemblies();
foreach (Assembly ass in assemblies)
{
    if (ass.GetName().Name == "Unity.Model") { this.modelAssembly = ass; }
    if (ass.GetName().Name == "Unity.ModelView") { this.modelViewAssembly = ass; }
}
```

直接从当前 AppDomain 里找到 Unity 已经编译好的程序集，不做文件加载。这是日常开发最常用的模式——改代码后 Unity 自动重新编译，运行时就自动用新程序集了。

**EnableDll 在哪设置？**

`GlobalConfig` 是一个 ScriptableObject：

```text
Unity/Assets/Resources/GlobalConfig.asset
```

在 Inspector 里勾选 `EnableDll` 可切换。Switch 开关的另一面是 `AssemblyEditor`——当 EnableDll 为 true 时，它会在进入 Play Mode 前把 `Library/ScriptAssemblies/` 下的同名 dll 改名为 `.DISABLE`，防止 Unity 自己的程序集和 dll.bytes 冲突。

**三种模式对比：**

```text
┌──────────────────┬──────────────────────────────┬─────────────────────┐
│ 运行环境          │ 加载来源                      │ 何时需要             │
├──────────────────┼──────────────────────────────┼─────────────────────┤
│ Editor 默认       │ AppDomain 已有程序集           │ 日常开发，改完即跑    │
│ Editor + EnableDll│ Assets/Bundles/Code/*.bytes  │ 验证 dll 加载流程    │
│ 真机 / 包         │ Bundles 资源系统              │ 正式运行             │
└──────────────────┴──────────────────────────────┴─────────────────────┘
```

## 3. ET/Compile 做了什么

`ET/Compile` 菜单绑定在 `AssemblyTool.MenuItemOfCompile()`，快捷键 F6。

它调用的 `DoCompile()` 分三步：

**第一步：RefreshCodeMode**

根据 `GlobalConfig.CodeMode`（Client / Server / ClientServer）决定启用哪些 asmdef 程序集定义文件。本质是控制哪些代码目录参与编译：

```text
ClientServer（默认）：启用四组源码目录全部参与编译
Client：只编译客户端相关目录，排除 Server 目录
Server：只编译服务端相关目录，排除 Client/ModelView/HotfixView 目录
```

实现方式是通过删除/恢复 `.asmdef` 文件来开关编译单元。

**第二步：CompileDlls**

调用 Unity 的 `PlayerBuildInterface.CompilePlayerScripts()`，把四个程序集编译到：

```text
Temp/Bin/Debug/Unity.Hotfix.dll
Temp/Bin/Debug/Unity.HotfixView.dll
Temp/Bin/Debug/Unity.Model.dll
Temp/Bin/Debug/Unity.ModelView.dll
```

注意这和 dotnet 服务端编译不同——这里走的是 Unity 的编译管线，产物在 `Temp/Bin/Debug/`。

**第三步：CopyHotUpdateDlls**

把编译产物从 `Temp/Bin/Debug/` 复制到 `Assets/Bundles/Code/`，并改成 `.dll.bytes` 后缀：

```csharp
static void CopyHotUpdateDlls()
{
    FileHelper.CleanDirectory(Define.CodeDir);  // 清空旧文件
    foreach (string dllName in DllNames)
    {
        string sourceDll = $"{Define.BuildOutputDir}/{dllName}.dll";
        string sourcePdb = $"{Define.BuildOutputDir}/{dllName}.pdb";
        File.Copy(sourceDll, $"{Define.CodeDir}/{dllName}.dll.bytes", true);
        File.Copy(sourcePdb, $"{Define.CodeDir}/{dllName}.pdb.bytes", true);
    }
    AssetDatabase.Refresh();
}
```

加 `.bytes` 后缀是因为 Unity 会把 `.bytes` 文件当成 `TextAsset` 处理，方便通过资源系统加载——这就是为什么前面 `CodeLoader` 用 `ResourcesComponent.LoadAllAssetsAsync<TextAsset>` 来加载 dll。

## 4. 你的第一次客户端热更：改一个 UI 行为

假设登录按钮目前点了没反应，你发现是 System 里的回调逻辑写错了。走一遍完整流程。

**要改的代码：**

登录按钮的回调逻辑在 HotfixView 里，比如：

```text
Unity/Assets/Scripts/HotfixView/Client/Agar/UI/UIAgarLogin/UIAgarLoginComponentSystem.cs
```

这是 `Unity.HotfixView` 程序集里的代码，属于可热更范围。

**修改代码：**

```csharp
// 修改前：点了按钮没反应，漏了调用
self.loginBtn.GetComponent<Button>().onClick.AddListener(() =>
{
    Log.Debug("button clicked");  // 只打了日志
});

// 修改后：补上实际登录逻辑
self.loginBtn.GetComponent<Button>().onClick.AddListener(() =>
{
    self.OnLoginClick().Coroutine();
});
```

保存文件。

**编译：**

在 Unity 编辑器中执行 `ET/Compile`（快捷键 F6）。你会看到 Console 输出：

```text
Compile Finish!
```

此时检查 `Assets/Bundles/Code/` 目录，确认文件时间戳已更新：

```text
Unity.HotfixView.dll.bytes  ← 修改时间应该是最新的
Unity.HotfixView.pdb.bytes
```

**触发热更：**

如果 Unity 正在 Play 模式，按 F7（`ET/Reload`），Console 输出：

```text
reload dll finish!
```

新代码已经生效。点击登录按钮，`OnLoginClick` 逻辑被执行。

**如果不在 Play 模式：**

对于 Editor 默认模式（EnableDll = false），直接点击 Play 按钮即可。因为模式三直接从 AppDomain 加载程序集，Unity 在你保存代码后已经自动重新编译了，Play 时自动使用最新程序集。

## 5. ET/Reload（F7）做了什么

F7 调用的代码在 `AssemblyTool.MenuItemOfReload()`：

```csharp
[MenuItem("ET/Reload _F7", false, ETMenuItemPriority.Compile)]
static void MenuItemOfReload()
{
    if (Application.isPlaying)
    {
        CodeLoader.Instance?.Reload();
    }
}
```

只在 Play 模式下有效。它调用客户端的 `CodeLoader.Reload()`：

```csharp
public void Reload()
{
    // 重新加载 Hotfix 和 HotfixView 程序集
    (Assembly hotfixAssembly, Assembly hotfixViewAssembly) = this.LoadHotfix();

    // 用新程序集重建 CodeTypes
    CodeTypes codeTypes = World.Instance.AddSingleton<CodeTypes, Assembly[]>(new[]
    {
        typeof(World).Assembly, typeof(Init).Assembly,
        this.modelAssembly, this.modelViewAssembly,
        hotfixAssembly, hotfixViewAssembly
    });

    // 重新执行 [Code] 特性的 CreateCode
    codeTypes.CreateCode();

    Log.Info($"reload dll finish!");
}
```

服务端 `CodeLoader.Reload()` 用 `AssemblyLoadContext.Unload()` 来卸载旧程序集。客户端 `LoadHotfix()` 没有卸载步骤——它直接用新的 `Assembly.Load` 覆盖引用。这是因为在 Editor 默认模式下，程序集引用来自 AppDomain 本身，不存在独立的 LoadContext 可以卸载。只有在 EnableDll 模式下，每次重新读取 `.dll.bytes` 文件得到的是新内容。

## 6. 日常开发流程总结

根据你的 `EnableDll` 设置不同，日常流程略有差异。

**默认模式（EnableDll = false，最常用）：**

```text
1. 修改 Hotfix 或 HotfixView 下的 .cs 文件
2. Unity 自动重新编译（或手动 Ctrl+R 强制刷新）
3. 点击 Play 按钮
4. 如需在运行中热更：F6 编译 → F7 Reload
```

**EnableDll 模式（验证 dll 加载流程时）：**

```text
1. 修改 Hotfix 或 HotfixView 下的 .cs 文件
2. F6（ET/Compile）
3. 确认 Assets/Bundles/Code/*.dll.bytes 已更新
4. 点击 Play 按钮（或 Play 中按 F7 Reload）
```

两种模式的核心区别：
- 默认模式下，Unity 帮你管编译和加载，改完代码 Play 就是最新的。
- EnableDll 模式下，你必须手动 F6 生成 dll.bytes，CodeLoader 才会加载新代码。
- 默认模式下，`Model` 和 `ModelView` 改了也是即时生效的（因为直接从 AppDomain 加载，不区分"热更"）。EnableDll 模式下这四个程序集全部从 dll.bytes 加载。

## 7. IL2CPP 打包后的热更：HybridCLR

在 Editor 里热更相对简单，但打包成 IL2CPP 后情况不同。IL2CPP 把 C# 编译成 C++ 再编译成本地代码，不再有动态加载 C# 程序集的天然能力。

HybridCLR 填补了这个 gap。它让 IL2CPP 平台也能在运行时加载 C# 热更新程序集。

**需要 HybridCLR 的场景：**

```text
打 IL2CPP 包（Android / iOS / Windows IL2CPP）
需要运行时加载 Hotfix.dll / HotfixView.dll
AOT 泛型需要用补充元数据
```

**Mono 打包不需要 HybridCLR**——Mono 本身支持动态加载。

**本仓库的 HybridCLR 相关文件：**

```text
Unity/Assets/Scripts/Editor/Plugins/HybridCLR/HybridCLREditor.cs  — CopyAotDlls 菜单
Unity/Assets/Bundles/AotDlls/                                       — AOT 补充元数据
Unity/Assets/Scripts/Loader/CodeLoader.cs                            — RuntimeApi.LoadMetadataForAOTAssembly
```

CodeLoader 中，当检测到 IL2CPP 环境时：

```csharp
if (Define.EnableIL2CPP)
{
    foreach (var kv in this.aotDlls)
    {
        TextAsset textAsset = kv.Value;
        RuntimeApi.LoadMetadataForAOTAssembly(textAsset.bytes, HomologousImageMode.SuperSet);
    }
}
```

这会为 AOT 程序集补充元数据，解决 IL2CPP 裁剪导致的泛型实例化失败等问题。

**打包前的 HybridCLR 准备流程（来自 ET 运行指南）：**

```text
1. HybridCLR Installer         — 安装 HybridCLR 到项目
2. HybridCLR Generate All      — 生成所有所需的桥接代码
3. HybridCLR CopyAotDlls       — 复制 AOT 补充元数据 dll 到 Bundles/AotDlls
4. ET/Compile                  — 编译热更程序集并生成 dll.bytes
```

## 8. 什么改动可以热更 / 不可以热更

**适合热更的改动：**

```text
修改 Hotfix 里的 Handler 逻辑
修改 Hotfix 里的 System 行为
修改 HotfixView 里的 UI 创建、按钮回调
新增 UIEvent、新增 ComponentSystem、新增 Handler
修复 Bug
调整参数
```

**不适合热更的改动：**

```text
修改 Loader 程序集的代码（CodeLoader、Init、Program 等启动链路）
修改 Core 程序集的代码（Entity、Fiber、World 等框架基础）
修改 Model/ModelView 里的 Entity/Component 字段结构
修改 Unity 原生插件（C++ DLL / .jar / .a）
修改资源打包流程（YooAsset 配置等）
修改 AOT 泛型的使用方式但没有补充元数据
```

一个实际例子：如果你在 `UIAgarLoginComponent` 里加了一个新字段 `RememberMe`，然后改了 HotfixView 里的 System 在登录时读取这个字段——这需要 `ModelView` 程序集重新编译。在 Editor 默认模式下这不是问题（Unity 统一编译所有程序集），但在 EnableDll 模式或打包后，你需要 F6 重新编译全部四个程序集，而不只是 HotfixView。

## 9. 代码热更和资源热更是两回事

新人常把"热更"理解成一种东西，实际上 ET 项目里至少有两层独立的热更：

```text
代码热更：替换 dll.bytes → CodeLoader.Reload() → 新逻辑生效
资源热更：替换 Prefab / 贴图 / 配置表 / AssetBundle → 资源系统重新加载
```

`CodeLoader` 只管代码加载链路。资源热更涉及的是 YooAsset 的资源版本管理、Bundle 下载和缓存机制，和 C# dll 热更是完全独立的流程。

判断一个问题是代码层面还是资源层面：
- 新 Handler 不触发、新 System 不执行 → 代码热更排查
- Prefab 没更新、新 UI 不显示、贴图不对 → 资源热更排查

## 10. 完整流程总结

```text
你在 IDE 里改 Hotfix / HotfixView 代码
                │
                ▼
         F6: ET/Compile
    AssemblyTool.DoCompile()
        ├─ RefreshCodeMode()    根据 CodeMode 开关 asmdef
        ├─ CompileDlls()        PlayerBuildInterface 编译四个程序集
        └─ CopyHotUpdateDlls()  复制到 Assets/Bundles/Code/*.dll.bytes
                │
                ▼
        Assets/Bundles/Code/*.dll.bytes 已更新
                │
                ▼
         F7: ET/Reload（Play 模式下）
    CodeLoader.Reload()
        ├─ LoadHotfix()          重新加载 dll.bytes 或从 AppDomain 获取
        ├─ 重建 CodeTypes        重新扫描 Handler、System、Event
        └─ codeTypes.CreateCode()    重新执行 [Code] 注册
                │
                ▼
         Log: "reload dll finish!"
                │
                ▼
        后续 UI 交互和消息处理使用新代码
```

## 11. 新人排查清单

1. 改了代码没生效 → 先执行 F6（ET/Compile），确认 `Assets/Bundles/Code/*.dll.bytes` 修改时间是最新的。
2. F7 Reload 没有反应 → 确认正在 Play 模式（F7 只在 `Application.isPlaying` 时有效）。
3. F7 报 NullReferenceException → `CodeLoader.Instance` 为 null，说明 Play 模式还没初始化完成，等启动流程跑完再按。
4. Editor 里没走 dll 加载 → 检查 `GlobalConfig.EnableDll`。默认 false 时代码直接从 AppDomain 加载，不需要 F6。
5. IL2CPP 包里异常（MissingMethod、泛型相关）→ 检查 HybridCLR 的 AOT 元数据是否复制到 `Assets/Bundles/AotDlls/`。
6. 修改了 Model/ModelView 里的类型字段 → 在 EnableDll 或打包模式下，需要 F6 重新编译 Model/ModelView 的 dll.bytes，不能只编译 Hotfix。
7. 修改了 Loader 或 Core 代码 → 这些程序集不在热更范围内，需要重新打包。不要在运行时指望替换它们。
8. UI Prefab 不更新 → 这是资源热更问题，不是代码热更问题。检查资源打包和加载流程。
9. Play 模式下 F6 编译失败 → 检查 Console 错误。编译失败时不会有新 dll.bytes 生成，按 F7 重载的还是旧代码。
10. 生产热更前 → 先在 EnableDll 模式下的 Editor 里完整验证一遍 F6 → Play → F7 → 确认效果 的完整流程。
