# 服务端如何热更

这篇带你走一遍服务端热更的完整流程：从代码修改、编译、到运行中的服务端加载新 DLL。

先记住结论：服务端是 dotnet 进程，热更的目标是替换 `Hotfix.dll`，让框架重新扫描新的 Handler 和 System，后续所有消息处理自动使用新代码。

和客户端热更的对比可以先记一个：

```text
客户端：Unity 里写代码 -> ET/Compile -> 生成 dll.bytes -> CodeLoader 加载
服务端：写代码 -> dotnet build -> 替换 Bin/Hotfix.dll -> 控制台输入 ReloadDll -> CodeLoader 重载
```

## 1. 服务端启动时发生了什么

在看热更之前，先搞清楚服务端启动时到底加载了哪些程序集。这样你才能理解"热更"到底替换了什么。

服务端入口在：

```text
DotNet/App/Program.cs
DotNet/Loader/Init.cs
DotNet/Loader/CodeLoader.cs
```

启动流程分三步走。

**第一步：Program.Main**

`DotNet/App/Program.cs` 的 `Main()` 做了三件事：

```csharp
Entry.Init();       // 预加载 Model 程序集，防止被裁剪
Init init = new();
init.Start();       // 初始化日志、FiberManager、CodeLoader

while (true)        // 主循环
{
    init.Update();
    init.LateUpdate();
}
```

`Entry.Init()` 的存在是因为 DotNet.App 不直接引用 Model 程序集。如果不在这里调用一下 Entry，dotnet 可能认为 Model 没被用到就不加载它，后续 CodeLoader 反射调用就会失败。

**第二步：Init.Start**

`DotNet/Loader/Init.cs` 里做的事情很直接：

```text
注册 UnhandledException 回调
解析命令行参数（AppType、Process 等）
创建 Logger
创建 TimeInfo
创建 FiberManager
创建 CodeLoader  ← 关键
```

`CodeLoader` 的创建触发了服务端第一次加载 Hotfix.dll。

**第三步：CodeLoader.Awake**

`DotNet/Loader/CodeLoader.cs` 的 `Awake()` 是整个加载的核心：

```csharp
public void Awake()
{
    // 1. 从当前 AppDomain 找到 Model 程序集
    Assembly[] assemblies = AppDomain.CurrentDomain.GetAssemblies();
    foreach (Assembly ass in assemblies)
    {
        if (ass.GetName().Name == "Model")
        {
            this.assembly = ass;
            break;
        }
    }

    // 2. 加载 Hotfix.dll
    Assembly hotfixAssembly = this.LoadHotfix();

    // 3. 用所有程序集创建 CodeTypes
    World.Instance.AddSingleton<CodeTypes, Assembly[]>(
        new[] { typeof(World).Assembly, typeof(Init).Assembly, this.assembly, hotfixAssembly }
    );

    // 4. 反射调用 ET.Entry.Start，启动所有 Fiber
    IStaticMethod start = new StaticMethod(this.assembly, "ET.Entry", "Start");
    start.Run();
}
```

`LoadHotfix()` 做了什么？

```csharp
private Assembly LoadHotfix()
{
    assemblyLoadContext?.Unload();        // 如果之前加载过，先卸载
    GC.Collect();                         // 强制垃圾回收，释放旧程序集
    assemblyLoadContext = new AssemblyLoadContext("Hotfix", true);
    byte[] dllBytes = File.ReadAllBytes("./Hotfix.dll");
    byte[] pdbBytes = File.ReadAllBytes("./Hotfix.pdb");
    Assembly hotfixAssembly = assemblyLoadContext.LoadFromStream(
        new MemoryStream(dllBytes), new MemoryStream(pdbBytes)
    );
    return hotfixAssembly;
}
```

关键细节：
- 使用 `AssemblyLoadContext`（.NET 的可回收程序集加载上下文），而不是直接 `Assembly.Load`。这样才能在重载时完全卸载旧程序集。
- 第二个参数 `true` 表示"可回收"，调用 `Unload()` 后 GC 可以真正释放。
- 同时加载 `.pdb` 是为了保留调试符号，出错时能看到行号。

**所以服务端启动后，内存中有这些程序集：**

```text
Core（World、FiberManager 等框架基础，来自 Loader 自身）
Loader（Init、CodeLoader 等启动逻辑，来自 DotNet.Loader）
Model（Entity、Component、协议定义，来自 DotNet.Model）
Hotfix（Handler、System、业务逻辑，来自动态加载的 Hotfix.dll）
```

## 2. 你的第一次热更：改一个 Handler

假设你在调试匹配功能，发现匹配超时时间太短。让我们实际走一遍"修改 -> 编译 -> 热更 -> 验证"。

**要改的代码在：**

```text
Unity/Assets/Scripts/Hotfix/Server/Agar/Gate/C2G_AgarMatchHandler.cs
```

这段代码在 Hotfix 程序集里，属于可以热更的范围。

**修改代码：**

把匹配超时时间从 10 秒改成 20 秒（这只是个例子，真实代码里可能是改配置）：

```csharp
// 修改前
await fiber.Root.GetComponent<TimerComponent>().WaitAsync(10000);

// 修改后
await fiber.Root.GetComponent<TimerComponent>().WaitAsync(20000);
```

保存文件。

**编译 Hotfix 程序集：**

服务端 Hotfix 工程在：

```text
DotNet/Hotfix/DotNet.Hotfix.csproj
```

注意这个工程的特殊之处——它自己不包含任何源码文件，而是通过 `<Compile Include>` 引用 Unity 项目里的代码：

```xml
<Compile Include="..\..\Unity\Assets\Scripts\Hotfix\Client\**\*.cs">
<Compile Include="..\..\Unity\Assets\Scripts\Hotfix\Server\**\*.cs">
<Compile Include="..\..\Unity\Assets\Scripts\Hotfix\Share\**\*.cs">
```

这意味着你在 Unity 工程里写的 Hotfix 代码，会被 DotNet.Hotfix 工程编译。

编译命令：

```bash
dotnet build DotNet/Hotfix/DotNet.Hotfix.csproj
```

编译产物输出到：

```text
Bin/Hotfix.dll
Bin/Hotfix.pdb
```

**确认编译产物已更新：**

观察 `Bin/Hotfix.dll` 的修改时间，确认它确实是刚生成的：

```powershell
Get-ChildItem Bin/Hotfix.dll | Select-Object LastWriteTime
```

**触发热更：**

如果服务端正在运行，在控制台输入：

```text
ReloadDll
```

回车后，你会看到日志输出：

```text
reload dll finish!
```

到这里，新代码已经生效。后续进入匹配流程的玩家会使用 20 秒超时。

## 3. 控制台命令是怎么触发 Reload 的

你输入 `ReloadDll` 后，实际发生了什么？跟踪一下调用链。

**第一站：控制台读取输入**

`Unity/Assets/Scripts/Hotfix/Share/Module/Console/ConsoleComponentSystem.cs` 里有一个异步循环：

```csharp
private static async ETTask Start(this ConsoleComponent self)
{
    while (true)
    {
        string line = await Task.Factory.StartNew(() =>
        {
            Console.Write($"{modeContex?.Mode ?? ""}> ");
            return Console.In.ReadLine();
        });

        // 解析命令：第一个词是 mode，后面的词是参数
        string[] lines = line.Split(" ");
        string mode = modeContex == null ? lines[0] : modeContex.Mode;

        // 找到对应的 IConsoleHandler 执行
        IConsoleHandler iConsoleHandler = ConsoleDispatcher.Instance.Get(mode);
        await iConsoleHandler.Run(self.Fiber(), modeContex, line);
    }
}
```

当你输入 `ReloadDll` 时，`mode` 变量就是 `"ReloadDll"`。

**第二站：ConsoleDispatcher 找到 Handler**

`Unity/Assets/Scripts/Model/Share/Module/Console/ConsoleDispatcher.cs` 在启动时会扫描所有标记了 `[ConsoleHandler]` 的类：

```csharp
HashSet<Type> types = CodeTypes.Instance.GetTypes(typeof(ConsoleHandlerAttribute));
foreach (Type type in types)
{
    ConsoleHandlerAttribute attr = (ConsoleHandlerAttribute)type.GetCustomAttributes(...)[0];
    IConsoleHandler handler = (IConsoleHandler)Activator.CreateInstance(type);
    this.handlers.Add(attr.Mode, handler);
}
```

`ReloadDllConsoleHandler` 注册时用的 Mode 是 `"ReloadDll"`，所以 `ConsoleDispatcher.Instance.Get("ReloadDll")` 会返回它。

**第三站：ReloadDllConsoleHandler 执行**

`Unity/Assets/Scripts/Hotfix/Share/Module/Console/ReloadDllConsoleHandler.cs`：

```csharp
[ConsoleHandler(ConsoleMode.ReloadDll)]
public class ReloadDllConsoleHandler : IConsoleHandler
{
    public async ETTask Run(Fiber fiber, ModeContex contex, string content)
    {
        await ETTask.CompletedTask;
        CodeLoader.Instance.Reload();
    }
}
```

就一行关键调用：`CodeLoader.Instance.Reload()`。

**第四站：CodeLoader.Reload()**

回到 `DotNet/Loader/CodeLoader.cs`：

```csharp
public void Reload()
{
    // 卸载旧程序集，加载新 Hotfix.dll
    Assembly hotfixAssembly = this.LoadHotfix();

    // 重新创建 CodeTypes，扫描新程序集中的 Handler、System 等
    CodeTypes codeTypes = World.Instance.AddSingleton<CodeTypes, Assembly[]>(
        new[] { typeof(World).Assembly, typeof(Init).Assembly, this.assembly, hotfixAssembly }
    );

    // 执行所有带有 [Code] 特性的 CreateCode
    codeTypes.CreateCode();

    Log.Debug($"reload dll finish!");
}
```

## 4. CodeTypes 重建后发生了什么

`CodeTypes` 是 ET 框架的"类型注册表"。它在创建时会扫描提供的程序集中所有类型，建立映射表。

当 `Reload()` 重新创建 `CodeTypes` 时：

```text
新的 Handler 类型被发现 → 后续消息分发使用新 Handler
新的 System 类型被发现 → 后续 EntitySystem 调用使用新逻辑
新的 Event 类型被发现 → 后续事件触发使用新处理器
新的 ConsoleHandler 被发现 → 控制台命令指向新处理类
```

但请注意：**只有标记了对应特性的类型才会被重新发现。** 如果你新增了一个 Handler，但没有写 `[MessageSessionHandler(SceneType.Gate)]`，它不会被注册。

`codeTypes.CreateCode()` 还会调用所有带 `[Code]` 特性的类的 `Awake` 方法。这意味着 `ConsoleDispatcher` 这样的组件也会重新扫描和注册 Handler——所以如果你在 Hotfix 里加了一个新控制台命令，Reload 后也能生效。

## 5. 编译输出到哪：DLL 的来龙去脉

这是新人最容易搞混的地方。理清目录关系：

```text
源码位置（你写代码的地方）：
  Unity/Assets/Scripts/Hotfix/Server/**/*.cs
  Unity/Assets/Scripts/Hotfix/Share/**/*.cs

工程文件（控制如何编译）：
  DotNet/Hotfix/DotNet.Hotfix.csproj

编译输出（dotnet build 产物）：
  Bin/Hotfix.dll
  Bin/Hotfix.pdb

服务端运行时的加载路径（CodeLoader 里写的）：
  ./Hotfix.dll     ← 即 Bin/Hotfix.dll（因为服务端从 Bin 目录启动）
```

所以**完整操作流程**是：

```text
1. 修改 Unity/Assets/Scripts/Hotfix/ 下的 .cs 文件
2. 执行 dotnet build DotNet/Hotfix/DotNet.Hotfix.csproj
3. 确认 Bin/Hotfix.dll 已更新
4. 在运行中的服务端控制台输入 ReloadDll
5. 看到 "reload dll finish!" 日志
```

## 6. 通过协议消息触发 Reload

除了在控制台手动输入 `ReloadDll`，ET 还提供了通过内部消息触发热更的方式。这对于多进程集群运维很有用——比如你有一个管理进程，可以向所有服务进程群发重载消息。

消息定义在：

```text
Unity/Assets/Config/Proto/InnerMessage_S_20001.proto
```

```protobuf
// ResponseType A2M_Reload
message M2A_Reload // IRequest
{
    int32 RpcId = 1;
}

message A2M_Reload // IResponse
{
    int32 RpcId = 1;
    int32 Error = 2;
    string Message = 3;
}
```

`M2A_Reload` 是一个 `IRequest` 类型的消息，可以发给任何 App 节点并等待 `A2M_Reload` 响应。

实际项目中，你可以：

```text
写一个管理工具或管理进程，向目标进程 ActorLocationSender.Call(M2A_Reload)
目标进程收到后调用 CodeLoader.Instance.Reload()
返回 A2M_Reload 确认重载完成
```

这样不需要登录每台服务器手动敲控制台命令。消息发送方只要知道目标进程的地址即可。

## 7. 什么场景适合热更/不适合

这是实际开发中最实用的判断表。不要盲目热更所有改动。

**适合热更的改动：**

```text
修改 Handler 里的业务逻辑（匹配规则、计算公式）
修改 System 里的 Tick 行为（定时检查、状态机转换）
修复 Bug（空引用、数组越界、逻辑错误）
调整参数（超时时间、阈值）
新增 Handler、新增 System（只加不删不改已有结构）
新增 Event 处理器
新增控制台命令
```

**不适合热更的改动（需要停服更新或更谨慎的流程）：**

```text
修改 Entity 或 Component 的字段定义（已有对象的字段值不会自动迁移）
修改 Model 程序集里的任何类型（Model 在 CodeLoader 初始化时就固定了，热更替换不了）
修改协议消息的字段（客户端和服务端可能不一致）
修改数据库存储结构
修改对象生命周期（新增 Entity 类型的强制移除或重建）
修改启动链路（Program.cs、Init.cs 本身不可热更）
```

这里有一个实际例子帮你理解"状态不迁移"：

假设你有一个 `PlayerComponent`，现在里面有一个字段 `Score`：

```csharp
public class PlayerComponent : Entity
{
    public int Score;  // 已有玩家对象 .Score = 100
}
```

如果你**只是修改对 Score 的计算逻辑**，比如改了 System 里的 `UpdateScore()` 方法——可以热更。

但如果你**把字段名从 Score 改成 TotalScore**，或者**把 int 改成 long**——这就不能热更了。因为运行中已经存在的 Player 对象上的 `Score` 字段还是旧定义的内存布局，新代码访问 `TotalScore` 会得到默认值 0，而不是原来存的值。

所以热更的原则是：**改行为，不改结构。**

## 8. 多进程集群的热更注意事项

本仓库的服务端通常以多进程集群运行（App、Gate、Match 等各自是独立的 dotnet 进程）。热更时要额外注意：

```text
每个进程都有自己独立的 Hotfix.dll，需要分别替换和 Reload
只 Reload 一个进程可能导致同集群内不同进程运行不同版本的代码
如果修改了跨进程协议消息的语义，所有用到该消息的进程必须一致
建议：修改 Hotfix 后，对所有目标进程依次执行 Reload
```

对于一个简单的多进程本地开发环境，你可以写一个批处理脚本，依次向各进程的控制台发送 `ReloadDll` 命令。

## 9. 完整流程总结

用一张图串联所有步骤：

```text
你在 IDE 里改 Hotfix 代码
         │
         ▼
dotnet build DotNet/Hotfix/
         │
         ▼
Bin/Hotfix.dll 和 Bin/Hotfix.pdb 更新
         │
         ▼
服务端控制台输入 ReloadDll
         │
         ▼
ReloadDllConsoleHandler 执行
         │
         ▼
CodeLoader.Reload()
  ├─ 卸载旧 AssemblyLoadContext
  ├─ GC.Collect()
  ├─ 创建新 AssemblyLoadContext
  ├─ 读取新 Hotfix.dll 和 Hotfix.pdb
  ├─ 重新创建 CodeTypes
  └─ 执行 codeTypes.CreateCode()
         │
         ▼
新的 Handler、System、Event 被注册
         │
         ▼
Log: "reload dll finish!"
         │
         ▼
后续请求使用新代码
```

## 10. 新人排查清单

1. 改了代码没生效 → 确认执行了 `dotnet build`，确认 `Bin/Hotfix.dll` 的修改时间是最新的。
2. Reload 后报"找不到 Hotfix.dll" → 确认服务端从 `Bin/` 目录启动（CodeLoader 用的是 `./Hotfix.dll` 相对路径）。
3. 服务端启动时就加载了旧 DLL → 这是正常的，启动时加载一次，后续用 Reload 更新。不要在启动前手动替换 DLL。
4. 新 Handler 不触发 → 检查是否标记了 `[MessageSessionHandler]` 或 `[MessageHandler]` 并匹配正确的 `SceneType`。
5. Reload 后旧对象状态错乱 → 你可能改了 Component 字段结构。热更适合改行为逻辑，不适合改数据结构。
6. 控制台输入 ReloadDll 没反应 → 检查 `ReloadDllConsoleHandler` 是否在 Hotfix 程序集中被编译进去（路径在 `Unity/Assets/Scripts/Hotfix/Share/Module/Console/`）。
7. 多进程集群只 reload 了一个进程 → 可能导致逻辑不一致。建议全部进程都 reload。
8. 修改了 Model 层代码也执行了 Reload 还是旧的 → Model 程序集不是通过 AssemblyLoadContext 动态加载的，无法热更。需要重启服务端进程。
9. 编译 Hotfix 报错 → 检查 `DotNet/Hotfix/DotNet.Hotfix.csproj` 是否引用了你新写的代码所在的路径（它通过通配符 `**\*.cs` 引用，新增的 .cs 文件应该自动包含）。
10. 生产环境热更前 → 先在相同启动配置的开发环境里完整演练一遍。
