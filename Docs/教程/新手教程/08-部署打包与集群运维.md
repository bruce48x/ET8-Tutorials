# 部署打包与集群运维

这篇带你走一遍服务端打包部署的完整流程：从看懂 StartConfig、编译发布包，到本地启动集群、验证运行状态。

先记住结论：ET 的集群拓扑不是写死在代码里的，而是由 `Config/Json/s/StartConfig/` 下的配置文件定义。你换一套配置就能得到不同的进程和 Scene 布局。服务端通过 `Watcher`（守护进程）自动启动本机的所有子进程。

## 1. 理解 StartConfig 四件套

每个部署场景（Localhost / Release / Benchmark 等）都有四个配置文件。放在 `Config/Json/s/StartConfig/<场景名>/` 下。

本仓库 Localhost 示例在：

```text
Config/Json/s/StartConfig/Localhost/StartMachineConfig.txt
Config/Json/s/StartConfig/Localhost/StartProcessConfig.txt
Config/Json/s/StartConfig/Localhost/StartSceneConfig.txt
Config/Json/s/StartConfig/Localhost/StartZoneConfig.txt
```

文件内容是 JSON，每行一个配置项。我们来逐份读懂它们。

**StartMachineConfig：有哪些机器**

```json
[1, {"_t":"StartMachineConfig","_id":1,"InnerIP":"127.0.0.1","OuterIP":"127.0.0.1","WatcherPort":"10000"}]
```

回答了三个问题：
- 这台机器 id 是 1
- 内网 IP 是 127.0.0.1，外网 IP 也是 127.0.0.1（本地测试）
- Watcher 守护进程监听端口 10000

**StartProcessConfig：有哪些进程**

```json
[1, {"_t":"StartProcessConfig","_id":1,"MachineId":1,"Port":20001}]
```

- 只有一个进程，id 为 1
- 它运行在 Machine 1 上
- 进程端口 20001

**StartSceneConfig：每个进程里跑哪些 Scene**

```json
[1, {"_t":"StartSceneConfig","_id":1,"Process":1,"Zone":1,"SceneType":"Realm","Name":"Realm","Port":30002}]
[2, {"_t":"StartSceneConfig","_id":2,"Process":1,"Zone":1,"SceneType":"Gate","Name":"Gate1","Port":30003}]
[3, {"_t":"StartSceneConfig","_id":3,"Process":1,"Zone":1,"SceneType":"Gate","Name":"Gate2","Port":30004}]
[4, {"_t":"StartSceneConfig","_id":4,"Process":1,"Zone":1,"SceneType":"Location","Name":"Location","Port":0}]
[5, {"_t":"StartSceneConfig","_id":5,"Process":1,"Zone":1,"SceneType":"Match","Name":"Match","Port":0}]
[300, {"_t":"StartSceneConfig","_id":300,"Process":1,"Zone":3,"SceneType":"RouterManager","Name":"RouterManager","Port":30300}]
[301, {"_t":"StartSceneConfig","_id":301,"Process":1,"Zone":3,"SceneType":"Router","Name":"Router01","Port":30301}]
...
```

关键字段：
- `Process`：这个 Scene 跑在哪个进程里。上面全部是 1，说明所有 Scene 都在同一个进程里跑。
- `SceneType`：决定这个 Scene 的用途（Realm、Gate、Location、Match、Router 等）。
- `Port`：对外监听端口。`0` 表示不需要外部端口（如 Location 和 Match 只做内部通信）。
- `Zone`：区服 id。Zone 1 是本区，Zone 3 是 Router 专用区。

Reader 可以计算出来：Localhost 模式下，**一个 dotnet 进程承载了 Realm + 两个 Gate + Location + Match + RouterManager + 四个 Router，共 10 个 Scene**。生产环境可能会把这些 Scene 拆分到不同物理机的不同进程里。

**StartZoneConfig：有哪些区服**

```json
[1, {"_t":"StartZoneConfig","_id":1,"DBConnection":"mongodb://127.0.0.1","DBName":"ET1"}]
[2, {"_t":"StartZoneConfig","_id":2,"DBConnection":"","DBName":""}]
[3, {"_t":"StartZoneConfig","_id":3,"DBConnection":"","DBName":""}]
```

Zone 1 配置了 MongoDB 连接串和数据库名。Zone 2 和 Zone 3 没有数据库，因为它们不负责持久化。

**新手记这个对应关系就够了：**

```text
Machine  ──→  物理机或虚拟机（有 IP、有 Watcher 端口）
Process  ──→  一个 dotnet 进程（在 Machine 上运行，有一个端口）
Scene    ──→  进程内的逻辑服务（有 SceneType、有 Zone）
Zone     ──→  区服（有数据库连接）
```

## 2. 如何在本地启动服务端

理解了配置之后，我们实际启动一次。

**第一步：确认配置文件存在**

服务端启动时需要 `--StartConfig` 参数指定用哪套配置。默认值是：

```csharp
// Options.cs
[Option("StartConfig", Required = false, Default = "StartConfig/Localhost")]
public string StartConfig { get; set; }
```

所以不带 `--StartConfig` 参数时，默认使用 `Config/Json/s/StartConfig/Localhost/`。

**第二步：编译服务端**

```bash
dotnet build DotNet.sln
```

编译产物在 `Bin/` 目录。

**第三步：启动 Watcher**

Watcher 是 ET 的进程守护者。它的职责是：读取 StartConfig，找到本机 IP 对应的 Machine 配置，然后启动该 Machine 上所有的 Process。

启动 Watcher：

```bash
dotnet Bin/App.dll --AppType Watcher --StartConfig StartConfig/Localhost
```

也可以省略 `--StartConfig`，它会用默认的 Localhost。

Watcher 启动后做了什么？看 `WatcherComponentSystem.Awake()`：

```csharp
// WatcherComponentSystem.cs
string[] localIP = NetworkHelper.GetAddressIPs();
var processConfigs = StartProcessConfigCategory.Instance.GetAll();
foreach (StartProcessConfig startProcessConfig in processConfigs.Values)
{
    if (!WatcherHelper.IsThisMachine(startProcessConfig.InnerIP, localIP))
    {
        continue;  // 跳过不属于本机的 Process
    }
    System.Diagnostics.Process process = WatcherHelper.StartProcess(startProcessConfig.Id);
    self.Processes.Add(startProcessConfig.Id, process);
}
```

它会：
1. 获取本机所有 IP
2. 遍历所有 Process 配置
3. 判断 `InnerIP` 是否匹配本机
4. 匹配的就调用 `WatcherHelper.StartProcess` 启动

**第四步：Watcher 如何启动子进程**

`WatcherHelper.StartProcess`：

```csharp
const string exe = "dotnet";
string arguments = $"App.dll" +
    $" --Process={startProcessConfig.Id}" +
    $" --AppType=Server" +
    $" --StartConfig={Options.Instance.StartConfig}" +
    $" --Develop={Options.Instance.Develop}" +
    $" --LogLevel={Options.Instance.LogLevel}" +
    $" --Console={Options.Instance.Console}";

System.Diagnostics.Process process = ProcessHelper.Run(exe, arguments);
```

Watcher 为每个 Process 启动一个独立的 `dotnet App.dll --AppType Server --Process <id>` 子进程。

在 Localhost 配置中只有一个 Process，所以最终你会看到两个 dotnet 进程：
- 一个 Watcher 进程（你手动启动的）
- 一个 Server 进程（Watcher 启动的，里面跑了 10 个 Scene）

**第五步：验证启动成功**

观察 Console 日志输出。正常情况下你会看到类似的日志序列：

```text
[NLogger] 初始化完成
CodeLoader.Awake 加载 Model + Hotfix 程序集
ET.Entry.Start 开始
FiberManager 创建各个 Scene 的 Fiber
Realm 启动在端口 30002
Gate1 启动在端口 30003
Gate2 启动在端口 30004
...
```

你也可以用端口监听来确认：

```powershell
netstat -an | findstr "30002 30003 30004 30300"
```

如果看到这些端口处于 LISTENING 状态，说明服务端 Scene 已正常启动。

## 3. 如何打包发布（Linux）

服务端通常部署在 Linux 上。仓库根目录有打包脚本：

```text
Publish-linux-x64.ps1
```

它做的事很简单：

```powershell
# 1. 编译 linux-x64 发布版
dotnet publish -r linux-x64 --no-self-contained --no-dependencies -c Release

# 2. 复制编译产物到发布目录
Copy-Item .\Bin\linux-x64\publish -Destination .\Publish\linux-x64\Bin -Recurse -Force

# 3. 复制配置到发布目录
Copy-Item .\Config -Destination .\Publish\linux-x64\Config -Recurse -Force
```

执行后，发布包结构：

```text
Publish/linux-x64/
├── Bin/
│   ├── App.dll
│   ├── Hotfix.dll          ← 热更程序集
│   ├── Hotfix.pdb
│   ├── Model.dll
│   ├── Loader.dll
│   └── ... (所有依赖的 dll)
└── Config/
    └── Json/
        ├── s/StartConfig/  ← 服务端启动配置
        ├── c/               ← 客户端配置
        ├── cs/              ← 双端共享配置
        └── ...
```

目标服务器上只需要这个发布包和 .NET Runtime 即可运行。不需要 Unity、不需要源码。

**如果要打包 Windows 版本：**

```powershell
dotnet publish -r win-x64 --no-self-contained --no-dependencies -c Release
```

其他步骤完全相同。

## 4. 生产环境的多机部署

Localhost 把所有 Scene 塞在一个进程里。生产环境通常拆开。举个拆分示例：

**App 进程（Process 1）：**

```json
[1, {"_t":"StartSceneConfig","_id":1,"Process":1,"Zone":1,"SceneType":"Realm","Name":"Realm","Port":30002}]
[2, {"_t":"StartSceneConfig","_id":2,"Process":1,"Zone":1,"SceneType":"Location","Name":"Location","Port":0}]
```

**Gate 进程（Process 2、3 各一台机器）：**

```json
// Machine 2
[3, {"_t":"StartProcessConfig","_id":2,"MachineId":2,"Port":20001}]
[4, {"_t":"StartSceneConfig","_id":4,"Process":2,"Zone":1,"SceneType":"Gate","Name":"Gate1","Port":30003}]

// Machine 3
[5, {"_t":"StartProcessConfig","_id":3,"MachineId":3,"Port":20001}]
[6, {"_t":"StartSceneConfig","_id":5,"Process":3,"Zone":1,"SceneType":"Gate","Name":"Gate2","Port":30003}]
```

**Match 进程（Process 4）：**

```json
[7, {"_t":"StartProcessConfig","_id":4,"MachineId":4,"Port":20001}]
[8, {"_t":"StartSceneConfig","_id":6,"Process":4,"Zone":1,"SceneType":"Match","Name":"Match","Port":0}]
```

部署时，每台机器上放一份发布包，启动 Watcher。每台机器的 Watcher 会根据 `InnerIP` 匹配自己的 Machine 配置，然后只启动属于本机的 Process：

```bash
# 每台机器上都执行同样的命令
dotnet Bin/App.dll --AppType Watcher --StartConfig StartConfig/Release
```

多机部署的关键检查点：
- 各机器 `InnerIP` 和 `OuterIP` 是否正确
- 防火墙是否开放了 Scene 和 Process 的端口
- 各机器上 `Config/` 目录内容是否一致

## 5. 如何关闭服务端

**本地开发：**

直接 Ctrl+C 终止 Watcher 进程。Watcher 退出后，它启动的子进程（Server）不会自动退出——你需要在任务管理器里或者用 `kill` 命令结束剩余的 dotnet 进程。

**生产环境：**

不建议只用 `kill`。更稳妥的流程：

```text
1. 从负载均衡或入口摘掉待关闭的进程（停止接受新连接）
2. 等待已有玩家请求处理完毕或踢下线
3. 发送关闭信号给进程
4. 确认进程退出
5. 如果超时未退出，强制 kill
```

生产环境通常会配合 systemd、supervisor、Docker 或自研运维系统做进程管理。本仓库目前只提供基础启动逻辑，优雅停机脚本需要结合你的具体运维平台来实现。

## 6. 进程崩溃怎么办

崩溃恢复分两层：

**进程内记录：**

`DotNet/Loader/Init.cs` 中设置了异常处理：

```csharp
AppDomain.CurrentDomain.UnhandledException += (sender, e) =>
{
    Log.Error(e.ExceptionObject.ToString());
};

ETTask.ExceptionHandler += Log.Error;
```

崩溃前至少会把异常写入日志。

**进程外守护：**

Watcher 的作用不仅仅是启动进程，它也是进程守护的基础。生产上你可以让 Watcher 定期检查子进程存活状态，死了就重新 `StartProcess`。或者把进程管理交给 systemd / supervisor 这类成熟的守护工具。

## 7. 监控应该看什么

最基本的三层监控：

| 层级 | 指标 | 检查方式 |
| --- | --- | --- |
| 进程层 | 进程是否存活 | 检查 dotnet 进程是否存在 |
| 网络层 | 端口是否监听 | `netstat` 检查 Scene 端口 |
| 业务层 | 在线玩家数、房间数、匹配队列长度 | 加监控消息或在日志中埋点 |

ET 的 `StartSceneConfig` 能告诉你应该有哪些进程和端口。把这份配置作为期望状态，对比实际运行状态，就是最基础的监控。

## 8. 完整流程总结

```text
本地开发：
  改代码 → dotnet build → Watcher 启动 → 自动拉起所有 Server 进程 → 验证

打包：
  dotnet publish -r linux-x64 → 复制 Bin + Config 到发布目录 → 压缩上传到服务器

服务器部署：
  解压发布包 → dotnet Bin/App.dll --AppType Watcher --StartConfig StartConfig/Release
  → Watcher 根据 Machine IP 自动启动本机 Process → 各 Server 进程创建自己的 Scene
  → 检查端口 → 开始接受连接

运维：
  监控进程和端口 → 崩溃时 Watcher 或系统守护自动拉起
  → 更新：替换 Hotfix.dll + ReloadDll（热更）或停服替换全部文件后重启
```

## 9. 新人排查清单

1. 服务端启动后客户端连不上 → 先确认 `StartSceneConfig` 里的端口号，再检查防火墙。
2. Process 启动失败 → 检查 `AppType`、`StartConfig`、`Process` 三个命令行参数。
3. Watcher 启动后没有拉起任何子进程 → 检查本机 IP 是否匹配 `StartMachineConfig` 的 `InnerIP`。
4. 本地正常、打包后连不上 → 检查 `Config/` 目录是否完整复制到发布目录。
5. 多机部署某台机器连不上其他机器 → 检查 `InnerIP`、`OuterIP`、防火墙策略。
6. 进程崩溃没有恢复 → 确认 Watcher 进程是否还活着，确认子进程是被谁管理的。
7. Scene 报端口占用 → 检查是否有残留的 dotnet 进程占着同一端口。先 kill 干净再启动。
8. 改了配置但没生效 → 确认改的是 `Config/Json/s/` 下对应场景的配置（不是 `cs/` 或 `c/`）。
9. 找不到 MongoDB → 检查 MongoDB 是否已安装并启动。`StartZoneConfig` 里的 `DBConnection` 是否正确。
10. 生产上线前 → 先在本地用 `Release` 配置走通完整流程（打包 → 复制 → Watcher 启动 → 验证）。
